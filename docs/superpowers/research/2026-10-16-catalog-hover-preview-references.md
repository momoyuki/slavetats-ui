# Catalog hover preview references — 2026-10-16

Research for design only. No implementation, build or deployment; no external code copied.

## Primary reference

Inspected SlavetatsUIPzx revision `3bca8156dc154dc5904e0e125e123ee378a82989`. Links below are pinned to that revision.

### Hover, pin and quick appearance

- The grid records the hovered identity independently from the clicked selection. Click calls SelectTattoo; hover only sets temporary section/name. [DrawPatternGrid](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_browser.cpp#L1209-L1221).
- Preview priority is hovered tattoo, otherwise selected unsaved edits, otherwise saved records. A settled-key debounce suppresses rapid tile crossings, and the key includes slot, identity, ink, glow and glossy. [UpdatePreview and Settled](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_browser.cpp#L1696-L1766).
- Ink and Glow are color controls; black glow means no glow. Glossy is a boolean. UI explicitly says Previewing - not saved. [Footer](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_browser.cpp#L1272-L1305).
- Important mismatch with our requested persistence: SelectTattoo resets ink/glow/glossy to the clicked definition's defaults. Hover uses the current slot's edited values. Therefore blindly reproducing that path could change the colors on click rather than pin exactly what was previewed. Our design must specify that pin captures the effective preview identity AND appearance. [SelectTattoo](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_model.cpp#L465-L474), [PreviewSlot](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_model.cpp#L729-L742).

### Runtime preview versus persistence

- PreviewSlot rejects external/locked slots and queues a texture/color/glow/gloss overlay paint, explicitly without a tattoo record. There is no BeginPreview transaction API in this path; Previewing plus painter state tracks the lifecycle. [PreviewSlot](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_model.cpp#L729-L742).
- The painter coalesces to the newest pending request, limits paint cadence to 250 ms, resolves the actor on the game thread, requires loaded 3D, takes an overlay lock, skips equivalent paint keys and applies deferred NiOverride overlay changes. Preview is a real visual runtime mutation even though tattoo records are untouched. [Painter](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_model.cpp#L273-L406).
- StopPreview uses EndPreviewQuick to redraw changed slots from saved records, falling back to a full SlaveTats synchronization. Browser close also calls EndPreview. [StopPreview](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_browser.cpp#L1688-L1693), [restore](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_model.cpp#L820-L849), [close](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_browser.cpp#L773-L801).
- Save captures the selected identity and quick values by value in ApplyRequest, cancels pending paints, performs the real tattoo operation and reads slots back. Persistent apply writes color/glow and optionally gloss before synchronizing. A preview must not paint after that synchronization. [ApplySlot](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_model.cpp#L535-L571), [ApplyTattoo](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_model.cpp#L210-L239).
- Glossy maps to glossiness/specularStrength 5 or 0; preview supplies empty advanced texture paths and emissive multiplier 1. These defaults cannot be assumed equivalent to our richer appearance contract or all packs. [Gloss mapping](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_model.cpp#L118-L131), [preview application](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/tattoo_model.cpp#L361-L378).

## Comparison with this repository

- `docs/superpowers/specs/2026-09-20-native-live-actor-preview-design.md` covers edits to an existing managed tattoo, with one-second debounce and typed update/commit/restore operations. These previews write authoritative appearance, unlike Pzx's record-free painter. The spec explicitly excludes temporary overlays outside SlaveTatsNG and arbitrary texture preview.
- `src/native/NativeSlotWorkflowModel.h`: PreviewTattooAppearance currently contains only color/alpha. TattooAppearance contains glow, glossiness, specularStrength, emissiveMult, glowTexture and bump. Existing AppearanceEditSession carries exact actor, generation, area, slot, handle and original values.
- `NativeSlotWorkflowModel::confirmApply()` currently sends only catalog identity plus color/alpha, with applyAndSynchronize or synchronizeOnly. `SlaveTatsService` has updateAppearance and loadout preview, but no catalog temporary-texture-preview contract. Merely adding footer controls would not retain glow/glossy through Save.

## Design hazards and required decisions

These are implications of the contracts, not claims that the external project is broken.

1. Do not drive hover by repeatedly applying/replacing real tattoos. This changes authoritative records/handles and would need reliable rollback after every failed or interrupted operation.
2. A temporary visual backend needs an explicit approved boundary behind service/runtime; do not put NiOverride/JContainers calls in the UI. Pzx's direct painter cannot be transplanted under our current non-goal without a design change.
3. Each queued preview/restore/save needs captured Actor form ID, target generation, preview session/revision and exact slot identity. Resolve/load-check at execution; never fall back to Player. Invalidate stale completions and never redirect an old actor's restore to the new actor.
4. Latest-wins preview cannot supersede a required restore or committed Save. Freeze/coalesce intents while one operation runs; remember the exact last effective preview and pin it on click. Save uses that pinned identity/value snapshot, not whatever tile is subsequently hovered.
5. Restore on hover-out returns to pinned preview if present, otherwise original saved appearance. Back/Close/target switch must finish restoration or expose a retryable failure. Actor unload and external slot changes must not silently discard cleanup obligations.
6. Record-free visual preview is still mutation: other runtime synchronization or game saving can observe intermediate visuals/override state. Decide whether such changes are persistent in the chosen backend and how unload/save/reload is handled; the absence of tattoo-record writes alone is not proof of non-persistence.
7. Keep typed partial-write versus synchronization-only failure handling. A successful Save followed by sync failure retries synchronization, never repeats apply or overwrites with late preview.
8. Define quick glossy mapping without erasing pack defaults, bump/glow paths, alpha, emissive multiplier or custom strengths. Detailed Edit Appearance should receive the saved readback, not freshly reconstructed defaults. Verify black-glow clearing, zero and >1 emissive multipliers, external read-only, and exact NPC identity.

## Save/co-save finding: persistent override writes are explicit

Following the painter into its helper resolves the persistence question: apply_overlay_ex_deferred calls AddNodeOverrideString/Int/Float with the last argument `true` for texture, ink, glow, emissive multiplier, alpha and glossy fields. The wrapper explicitly names that argument `a_persist` and forwards it unchanged. Thus this is NOT an isolated temporary renderer and NOT evidence for save/co-save-safe hovering; it writes persistent NiOverride state while avoiding SlaveTats tattoo records. Cleanup normally repaints from records or synchronizes afterward, but a save during the preview window can capture intermediate override state unless another mechanism intervenes. No save interception/isolation mechanism was established in the inspected path. [Overlay writer](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/src/overlays.cpp#L134-L164), [persist parameter forwarding](https://github.com/pethzero/SlavetatsUIPzx/blob/3bca8156dc154dc5904e0e125e123ee378a82989/include/nioverride_wrapper.h#L87-L100).

Design prerequisite for this repository: establish and verify a genuinely non-persistent preview backend (including save/co-save behavior) before promising catalog hover preview. Existing appearance preview's persistent JContainers update/rollback does not supply that guarantee. The user's confirmed immediate-hover behavior also differs from upstream's settled-key debounce plus 250 ms paint cadence; latest-wins scheduling should bound work without presenting that delay as the requested behavior.

## Bounded follow-up: RaceMenu genuinely separates persistence and visual writes

Reviewed official RaceMenu source `expired6978/SKSE64Plugins` at `9ebcb733e17be695f994cd2e9cc383043446bc02`.

- PapyrusNiOverride AddNodeOverride packs a variant, writes the persistent map only under `if (persist)`, then independently calls Impl_SetNodeProperty for currently loaded first/third-person geometry. Thus `persist=false` does have visual-only semantics in this implementation; it does not merely turn off some later serialization flag. [Actual branch](https://github.com/expired6978/SKSE64Plugins/blob/9ebcb733e17be695f994cd2e9cc383043446bc02/skee64/PapyrusNiOverride.cpp#L273-L305).
- Impl_AddNodeOverride writes `nodeData.m_data`; NodeRegistrationMapHolder::Save serializes that map as NDEN records, and OverrideInterface::Save invokes nodeData.Save. Bypassing Impl_AddNodeOverride bypasses this registry serialization path. [Map write](https://github.com/expired6978/SKSE64Plugins/blob/9ebcb733e17be695f994cd2e9cc383043446bc02/skee64/OverrideInterface.cpp#L56-L63), [map save](https://github.com/expired6978/SKSE64Plugins/blob/9ebcb733e17be695f994cd2e9cc383043446bc02/skee64/OverrideInterface.cpp#L2083-L2100), [save entry](https://github.com/expired6978/SKSE64Plugins/blob/9ebcb733e17be695f994cd2e9cc383043446bc02/skee64/OverrideInterface.cpp#L2312-L2317).
- Impl_SetNodeProperty finds the loaded node and either queues a shader-property task or writes its shader immediately. It does not update nodeData. The native public SetNodeProperty wrapper directly calls this implementation; native AddNodeOverride always adds to the registry and does not offer a persist argument. A C++ backend should investigate SetNodeProperty/GetNodeProperty rather than confuse native AddNodeOverride with the Papyrus persist=false wrapper. [Setter implementation](https://github.com/expired6978/SKSE64Plugins/blob/9ebcb733e17be695f994cd2e9cc383043446bc02/skee64/OverrideInterface.cpp#L750-L774), [native public wrappers](https://github.com/expired6978/SKSE64Plugins/blob/9ebcb733e17be695f994cd2e9cc383043446bc02/skee64/OverrideInterface.cpp#L2723-L2769).

Conclusion: there is a concrete upstream **candidate** nonpersistent shader-property backend. Pzx currently does not use that separation for its painter. This narrows the prerequisite, but does not establish compatibility with the installed RaceMenu ABI/version or prove every shader task/texture lifetime is safe during unload, save and restoration. Verify installed API availability, node/material ownership, deferred-task ordering, existing/missing overlay-node behavior, exact property readback and save/co-save in-game before declaring the capability supported. Do not replace persistent registry values or apply a registry-wide override after a visual-only preview, since doing so can overwrite the temporary material with saved values.
