# FLICK Launcher and UI Navigation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a direct FLICK launch action and improve every existing Tattoo Browser screen in one PR.

**Architecture:** FLICK only closes its menu and schedules the existing NativeMenu to open. SKSE Menu Framework continues rendering the workflow. Layout and navigation changes stay in the native adapter and deterministic presentation helpers; model/runtime behavior is reused.

**Tech Stack:** C++23, CommonLibSSE-NG, FLICK API v6, SKSE Menu Framework v3, CMake/vcpkg, CTest.

**Spec:** `docs/superpowers/specs/2026-10-14-flick-ui-design.md`

## Global Constraints

- FLICK is optional, dynamically loaded, and cannot block Menu Framework.
- Pin the FLICK API revision and preserve GPL attribution.
- FLICK callback cannot access workflow/model/runtime or thumbnails.
- Keep one menu session; deduplicate scheduled open commands.
- External slots remain read-only, actor handles are revalidated, and sync-only retry never repeats a mutation.

## Review Focus

- Missing or incompatible FLICK: plugin loads and the old entry/hotkey work.
- Rapid FLICK clicks: one open command and one session reset.
- FLICK menu close/open ordering: the browser opens after FLICK releases input.
- Narrow and ultrawide viewports: actor remains visible; controls are not clipped.
- All existing mutation states: confirmation, pending, error, retry, and safe close remain reachable.
